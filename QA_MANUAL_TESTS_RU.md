# Next Order Discount — чек-лист ручного QA

Версия чек-листа: 1.0  
Модуль: `set_next_order_discount` 1.0.0  
Поддерживаемая версия: PrestaShop 8.1+  
Назначение: функциональное, интеграционное и регрессионное ручное тестирование основных возможностей модуля.

Всего: 163 тест-кейса, включая отдельный smoke-набор из 12 критических сценариев.

## 1. Как пользоваться чек-листом

Для каждого теста заполнить:

- статус: `NOT RUN`, `PASSED`, `FAILED`, `BLOCKED`, `N/A`;
- фактический результат;
- ссылку на скриншот, видео, письмо или запись лога;
- номер дефекта, если результат отличается от ожидаемого.

Приоритеты:

- **P0** — критический сценарий; без него релиз блокируется;
- **P1** — основная функция;
- **P2** — дополнительная проверка, UX или редкий граничный сценарий.

Важно: прогонять тесты на отдельном QA-магазине. Смена времени, ручное редактирование данных и проверка удаления таблиц недопустимы на production.

## 2. Тестовое окружение и данные

### 2.1 Матрица окружений

Минимальный релизный прогон:

| Окружение | Назначение |
|---|---|
| PrestaShop 8.1, PHP 7.2, MySQL/MariaDB | Нижняя граница совместимости |
| Актуальная поддерживаемая PrestaShop 8.x, актуальный PHP | Основное окружение |
| Мультимагазин с двумя магазинами | Изоляция правил, купонов, настроек и статистики |
| Два языка магазина: RU и EN | Локализация писем и fallback |
| SMTP/почта в рабочем состоянии | Купонные письма, тесты и напоминания |
| SMTP намеренно сломан | Очередь, повторные попытки и ошибки |

Для каждого прогона записать версию PrestaShop, PHP, СУБД, браузер, тему, режим мультимагазина и способ доставки почты.

### 2.2 Подготовленные данные

Создать:

- клиентов `qa-new-ru@example.test` и `qa-new-en@example.test` без валидных заказов;
- клиента `qa-returning@example.test` минимум с двумя валидными заказами;
- клиента из группы `VIP` и обычного клиента из группы `Customer`;
- адреса доставки в двух странах, например Беларусь и Польша;
- валюты BYN и EUR;
- категорию `QA Category Included` и категорию `QA Category Excluded`;
- бренд `QA Brand Included` и бренд `QA Brand Excluded`;
- товары для каждой категории и бренда, а также товар без бренда;
- способы доставки с ненулевой стоимостью;
- статусы заказа `Payment accepted`, `Preparing`, `Canceled`, `Refunded`;
- почтовый ящик, в котором можно проверить HTML, plain-text часть и количество писем.

Перед каждым изолированным тестом использовать нового клиента/заказ либо явно удалить результаты предыдущего теста. Иначе защита от дублей по комбинации «магазин + заказ + правило» повлияет на результат.

### 2.3 Базовые правила

**R1 — Base 10%**

- активно;
- приоритет 1;
- скидка 10%;
- срок 30 дней;
- минимальная сумма следующего заказа 0;
- триггер `Payment accepted`;
- остальные условия `All`/пусто;
- `Stop after this rule = Yes`;
- код `NOD-%key%`, длина 8, тип alphanumeric;
- напоминания выключены.

**R2 — Fixed VIP**

- активно;
- приоритет 2;
- фиксированная скидка 15 в валюте заказа;
- срок 14 дней;
- минимум следующего заказа 50;
- группа `VIP` в режиме `Only the selected`;
- `Stop after this rule = No`.

**R3 — Reminder**

- активно;
- скидка 5%;
- срок 10 дней;
- напоминания включены: первое через 1 день, второе через 3 дня после основного письма;
- собственные RU/EN темы и HTML с плейсхолдерами.

## 3. Быстрый smoke-прогон

Перед полным регрессом выполнить: `INST-01`, `NAV-01`, `SET-01`, `RULE-02`, `GEN-01`, `GEN-04`, `CART-01`, `LIFE-01`, `CRON-03`, `COUP-01`, `DASH-01`, `LOG-01`.

Smoke считается успешным, если все P0-тесты пройдены и оформление заказа не ломается даже при ошибке почты.

## 8. Условия срабатывания

Во всех тестах этого раздела оставить только одно проверяемое ограничение, если не указано обратное. Границы Min/Max и From/To включительные.

| ID | Приоритет | Сценарий и шаги | Ожидаемый результат |
|---|---:|---|---|
| COND-01 | P0 | Выбрать один trigger status. Провести заказ через другой статус, затем через выбранный. | На другом статусе купона нет; на выбранном создаётся один купон. |
| COND-02 | P1 | Оставить trigger statuses пустыми и создать заказ в неоплаченном статусе. | Пустой список не ограничивает статус: правило срабатывает на первом событии заказа. Повторная смена статуса не создаёт дубль. |
| COND-03 | P1 | Выбрать два trigger status и последовательно перевести заказ в оба. | Купон создаётся при первом подходящем переходе; второй переход не создаёт ещё один купон по тому же правилу. |
| COND-04 | P1 | Source total Min = 100, Max = 200. Создать заказы 99.99, 100, 200, 200.01. | Купоны создаются только для сумм 100 и 200. |
| COND-05 | P1 | Active window = сегодня. Проверить заказ сегодня; затем задать окно в будущем и повторить новым заказом. | Сегодня правило срабатывает до конца дня; для будущего окна сейчас не срабатывает. |
| COND-06 | P1 | Customer order number Min = Max = 1. Сделать первый, затем второй валидный заказ одного клиента. | Купон выдаётся только на первый валидный заказ. |
| COND-07 | P1 | Customer groups = Include VIP. Создать заказ VIP и обычного клиента. | Купон получает только VIP. |
| COND-08 | P1 | Customer groups = Exclude VIP. Повторить два заказа. | Купон получает только клиент вне VIP. |
| COND-09 | P1 | Countries = Include Беларусь. Сделать заказы с адресами Беларуси и Польши. | Учитывается страна адреса доставки заказа; купон только для Беларуси. |
| COND-10 | P1 | Countries = Exclude Беларусь. Повторить. | Заказ Беларуси исключён, Польши включён. |
| COND-11 | P1 | Currencies = Include EUR. Сделать заказы в EUR и BYN. | Купон создаётся только для EUR. |
| COND-12 | P1 | Categories = Include `QA Category Included`. Заказы: товар из включённой, из другой, и смешанная корзина. | Купон для включённой и смешанной корзины; нет купона для корзины только из другой категории. |
| COND-13 | P1 | Categories = Exclude `QA Category Excluded`. Проверить чистую разрешённую и смешанную корзину. | Чистая разрешённая корзина проходит; наличие хотя бы одного товара из исключённой категории блокирует правило. |
| COND-14 | P1 | Brands = Include `QA Brand Included`; проверить включённый, другой и товар без бренда. | Купон только для заказа с включённым брендом. |
| COND-15 | P1 | Brands = Exclude `QA Brand Excluded`; проверить чистую и смешанную корзину. | Любое пересечение с исключённым брендом блокирует правило. |
| COND-16 | P2 | Для каждого списочного условия выбрать режим All, оставив элементы выделенными. | Список скрывается/игнорируется; правило не ограничивается ранее выбранными элементами. |
| COND-17 | P2 | Выбрать Include или Exclude, но не выбрать элементы. | Пустой список трактуется как отсутствие ограничения; форма и генерация работают без ошибки. |
| COND-18 | P0 | Одновременно задать подходящие статус, сумму, VIP, страну, валюту, категорию и бренд. Затем нарушать по одному условию на новом заказе. | Купон создаётся только когда выполнены все условия; логика между условиями — AND. |

## 9. Приоритет и несколько правил

| ID | Приоритет | Сценарий и шаги | Ожидаемый результат |
|---|---:|---|---|
| PRIO-01 | P1 | Создать три активных правила. Перемещать среднее вверх/вниз стрелками. | Приоритеты и порядок меняются последовательно, сохраняются после reload. Верхнюю запись нельзя поднять, нижнюю нельзя опустить. |
| PRIO-02 | P0 | Два подходящих правила: у первого по приоритету Stop = Yes. Создать заказ. | Создан только купон первого правила. |
| PRIO-03 | P0 | У обоих подходящих правил Stop = No. Создать новый заказ. | Создано два разных купона — по одному на каждое правило. |
| PRIO-04 | P1 | Первое правило не подходит, второе подходит и Stop = Yes. | Создан купон второго правила; Stop непрошедшего правила не влияет на поиск. |
| PRIO-05 | P1 | Выключить первое правило, оставить второе подходящим. | Выключенное правило пропущено; купон выдаётся по второму. |
| PRIO-06 | P1 | После генерации изменить/удалить правило. | Уже созданный cart rule сохраняет исходную скидку и срок; историческая строка Coupons открывается без 500. |

## 10. Формат кода купона

| ID | Приоритет | Сценарий и шаги | Ожидаемый результат |
|---|---:|---|---|
| CODE-01 | P0 | Код `NOD-%key%`, length 8, alphanumeric. Сгенерировать купон. | Формат `NOD-XXXXXXXX`; случайная часть ровно 8 символов A–Z/0–9; общий код уникален. |
| CODE-02 | P1 | Поочерёдно выбрать Alphabetic, Numeric, Alphanumeric и генерировать купоны. | Случайная часть использует только выбранный алфавит. |

| CODE-04 | P2 | Проверить length 1, 100, пустое и нечисловое значение. | Генерация безопасно использует границы 4/32 или встроенный default 8; код не пустой и не длиннее 64 символов. |
| CODE-05 | P1 | Шаблон без `%key%`, например `RETURN-`. | Случайная часть добавляется в конец: `RETURN-XXXXXXXX`. |

| SEC-03 | P1 | Ввести `<script>`, HTML и SQL-подобный текст в Rule name, description, фильтры и email. | Списки и логи экранируют данные, SQL-инъекции/XSS не выполняются; разрешённый HTML письма исполняется только в email preview/письме в ожидаемом sandbox-контексте. |
| SEC-04 | P1 | Быстро дважды отправить Save/перевод в статус/cron. | Нет двойных купонов по одному правилу и заказу, нет неконсистентных статусов, страница не падает. |
| SEC-05 | P1 | Удалить стандартный cart rule, оставив link-запись; затем запустить expiry/cancel/reminder. | Обработка завершается без фатальной ошибки; lifecycle остаётся консистентным, проблема отражена в логах при необходимости. |
| SEC-06 | P1 | Сломать одну задачу в пачке очереди на QA-стенде, оставив следующую валидной. | Ошибка одной задачи не останавливает остальные; валидная становится Done, ошибочная retry/Failed. |
| SEC-07 | P2 | Проверить admin UI в Chrome и Firefox/Safari актуальных версий. | Переключатели, вкладки, multi-select, fetch/AJAX, preview iframe и кнопки работают одинаково. |

## 21. Проверки данных при расследовании дефекта

Это необязательные read-only проверки. Использовать фактический префикс БД вместо `PREFIX_`.

- `PREFIX_snod_rule` — настройки и приоритет правила;
- `PREFIX_snod_rule_*` — выбранные условия и письма;
- `PREFIX_snod_coupon_link` — связь заказ → правило → cart rule и lifecycle timestamps;
- `PREFIX_cart_rule` / `PREFIX_cart_rule_shop` — фактические свойства и shop association купона;
- `PREFIX_snod_dispatch_queue` — task type, status, attempts, available_at, last_error, correlation_id;
- `PREFIX_snod_cron_lock` — активная блокировка;
- `PREFIX_snod_log` — level, channel, context и correlation.

Для одного заказа и одного правила должно выполняться:

- не более одной строки в `snod_coupon_link`;
- ровно один связанный `id_cart_rule`, если генерация успешна;
- terminal status не должен возвращаться назад в `created`/`emailed`/`reminded`;
- `used`, `expired`, `canceled` взаимно исключают друг друга;
- automatic email/reminder task не должен дублироваться с тем же correlation ID.

## 23. Критерии готовности релиза

Релиз допускается, если:

- 100% P0 пройдено;
- не менее 95% P1 пройдено, остальные P1 имеют согласованное решение;
- нет открытых Blocker/Critical;
- заказ оформляется и меняет статус даже при недоступной почте или внутренней ошибке модуля;
- не возникает двойных купонов и двойных автоматических писем;
- персональный купон нельзя применить чужому клиенту;
- terminal lifecycle и деактивация cart rule согласованы;
- секретный cron endpoint недоступен без корректного token;
- мультимагазин не смешивает правила, купоны и настройки;
- установка, штатное удаление и повторная установка проходят успешно.
